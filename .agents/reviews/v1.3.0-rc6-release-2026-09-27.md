# Pinova v1.3.0-rc6 release and staging evidence

Date: 2026-09-27 (Asia/Tehran).

## Scope

Pinova supplies purpose-bound mobile identity evidence to wpForo 3.2.1 and Dokan Lite 5.1.3 with WooCommerce 11.1.2. Independent, default-off switches appear in Pinova's Integrations settings tab. The same WordPress account remains the identity anchor. Ordinary login, registration and mobile proof never assign seller privileges; native Dokan conversion retains its nonce, required fields, vendor/product approval and existing order ownership. Forum activation preserves administrative moderation, forum groups and truthful email status. Runtime changes are confined to Pinova.

## Authorized staging acceptance

The authorized target is a dedicated test site running WordPress 7.1.2, WooCommerce 11.1.2, wpForo 3.2.1, Dokan Lite 5.1.3 and Woodmart 8.6.2. A fresh private database/configuration/plugin backup was verified outside the public web root immediately before installation. SMS configuration was copied from the separately authorized source without changing that source; no provider credentials belong in this report.

The independently verified RC6 ZIP was installed with integrations off. The published RC5 ZIP was then actually reinstalled and its active-plugin/schema boot checked against the retained database. RC6 was reinstalled and its exact build identity, activation and schema version 3 checked again. This is an installed-package rollback/forward check, in addition to CI's archived-package compatibility fixture. No database restore overwrote newer data. Maintenance was limited to the test site and cleared; no server service was restarted.

The initial fresh export attempt failed before installation. A diagnostic export succeeded using the panel database-client environment and WP-CLI's default tablespace handling; only zero-byte failed attempts were removed. The successful fresh SQL/plugin backups and their checksums were retained.

The installed-package CLI acceptance passed independent/off/combined switch states, account-bound purpose-specific mobile proof, automatic forum activation versus manual approval, preserved administrator holds, truthful email status, native Dokan conversion, preserved primary/secondary forum groups, native vendor/product approval, immutable login/User ID, retained existing order ownership, and repeated idempotent schema initialization. Temporary users, order and OTP rows were removed, and temporary settings restored. The local harness was corrected to seed a real secondary group instead of assuming wpForo returns an array for an empty group set; its interrupted first attempt was explicitly cleaned, and the rerun uses `finally` cleanup. This correction did not alter the published plugin.

Actual HTTPS acceptance passed the private native administrator login, authenticated session, rendered Integrations settings, and retained administrator access after enabling both adapters. Home, account and forum pages returned successful responses, the account page rendered the Pinova form, native password recovery remained available, unauthenticated mobile-proof REST requests returned 403 with correlation metadata, and logout without a nonce returned 403. The temporary administrator and its session were removed; its temporary native-login activation arm was restored/removed only if still owned by that fixture.

Both integration switches were then left enabled for the authorized scenario. Registration was previously disabled, so it was enabled through Pinova's general setting (including Pinova's existing synchronization to WordPress). Original options were privately backed up. The separate native-login blocking gate was not activated.

One authorized real OTP initiation was submitted to the public REST endpoint after registration was enabled. The SMS provider accepted it, the encrypted queue completed through normal WordPress cron without a manual trigger, and acceptance/completion were observed within 64.66 seconds of request initiation (an observation upper bound, not an exact provider latency). Voice and messenger channels were disabled. Only one of the authorized maximum three messages was used. Recipient receipt confirmation remains separate and pending; no account was created by this initiation-only delivery check.

Final file verification matched all 3,615 installed Pinova files to the independently downloaded release ZIP, with no extra files. Ten scoped upstream entry-point/integration/configuration fingerprints remained unchanged, covering wpForo, Dokan, WooCommerce, Woodmart, the target configuration and source-site configuration/Pinova entry point. Private backup checksums and restrictive permissions were reverified, and maintenance was confirmed absent.

Final guest HTTP checks confirmed 302 redirects to Pinova for native forum login, forum registration and the vendor dashboard. Runtime status confirmed both adapters active, registration enabled, schema 3, the native-login blocking gate off, zero temporary acceptance accounts, scheduled queue/log cleanup, and database-backed logging.

Acceptance used scoped, temporary synthetic records and suppressed outbound messages during synthetic CLI scenarios. Actual delivery used only the separately authorized recipient and message ceiling. Synthetic OTP verification is not evidence of SMS delivery or recipient receipt.
