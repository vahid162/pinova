# Pinova Development

Work from a repository checkout or disposable worktree, never from an installed production copy of the plugin. Also establish compute isolation: a separate path, worktree, or Docker project still shares host resources. If the checkout is on a production or multi-tenant host, do not run dependency installation, full PHPStan, full wp-env/integration matrices, reproducible builds, or other unbounded PHP/Composer jobs there; use GitHub Actions or a dedicated resource-isolated development host. Limit local work on a shared live host to lightweight, bounded source checks after confirming headroom.

## Start every task

1. Read the root [`AGENTS.md`](../../../AGENTS.md). Inspect `git status --short --branch`, the current branch, recent commits, tags, and GitHub release state. Verify snapshots against Git.
2. Read the references needed for the task:
   - [`references/project-map.md`](references/project-map.md) for architecture, legacy identifier behavior, persistence, and source routing.
   - [`references/quality-and-release.md`](references/quality-and-release.md) for CI, tests, packaging, staging, and releases.
   - [`references/logging.md`](references/logging.md) for structured events, privacy, retention, diagnostics, correlation IDs, and operational review.
   - If identity migration documentation exists on the active 1.3 development branch, read it completely before migration, merge, resume, or rollback work.
3. Classify the request as read-only review, diagnosis, implementation, migration, release, or production deployment. Permission for one class does not authorize another.
4. Preserve unrelated changes. Never clean, reset, overwrite, migrate, publish, or deploy to simplify inspection.
5. Establish the requested delivery boundary before reporting completion. For this project, a new version intended for installation or site testing is a GitHub-delivered release: local worktree changes and local ZIPs are intermediate evidence only.
6. Route vulnerabilities through root `SECURITY.md`; never place exploit details, credentials, private routes, or production identifiers in public issues, pull requests, logs, or artifacts.

## Non-negotiable invariants

- A WordPress User ID is the account anchor. Never rewrite `wp_users.user_login` as a side effect of OTP login, profile/mobile editing, fallback resolution, or migration.
- The Illuminate connection must be initialized on every fresh WordPress request before any Eloquent-backed service runs. Keep `utils/class-database.php` in Composer `autoload.files` as well as the legacy classmap, keep its side-effect initialization guarded by a real WordPress database context, and have `pinova.php` idempotently initialize it after loading Composer when the resolver is still absent. Assert the resolver immediately after plugin load in integration bootstrap and make the release build fail when the eager autoload entry is absent.
- In 1.2.3, a valid physical `pinova_mobile` user-meta value is an explicit override and takes precedence over every older fallback alias, including a mobile-shaped legacy username and Digits metadata. Read that physical row with a prepared database query; calling `get_user_meta()` or `get_metadata_raw()` from the virtual `get_user_metadata` path recurses. Once an override exists, an older mobile value must not remain a Pinova login alias.
- If one mobile deterministically matches multiple legacy User IDs, fail closed and emit `pinova/identity_conflict_detected`; never choose the first row. Multi-ID merge belongs to the separately tested 1.3 identity workflow.
- Password authentication must resolve the User ID first, then call `wp_signon()` with the real `user_login`, preserving 2FA, Wordfence, and standard login hooks.
- Public authentication and recovery responses must not reveal whether an identifier exists, has a password, or belongs to a native-only role. Native-only roles use Pinova's private administrator route, which executes the native WordPress login pipeline without exposing that policy through account-specific REST output. Never replace that route with a custom password check that bypasses Wordfence, 2FA, passkeys, or core authentication hooks. Password-reset filters must preserve an upstream `WP_Error` instead of casting it to a truthy boolean.
- Bind every OTP verification to its intended purpose. `/pinova/user/login/otp` accepts only login and registration records, while `/pinova/auth/forgot/verify` accepts only password-recovery records. Reuse an unexpired OTP only when its identifier and purpose both match; a purpose mismatch must fail before marking the record verified, incrementing its attempts, creating a user, creating a session, or issuing a reset key. Standalone, checkout-modal, and Woodmart/Flatsome partial recovery resend actions must explicitly retain the `forgotPassword` workflow rather than falling through to ordinary OTP login. Concurrent login and recovery codes remain independent; email subjects and bodies must name the exact purpose so users can distinguish them. Never copy a user's OTP to the administrator or another recipient.
- Generate Pinova logout links on the canonical trailing-slash `/logout/` route. An omitted or empty login/logout return target must resolve explicitly to the safe role-aware/site fallback before calling `wp_validate_redirect()`; WordPress preserves an empty location instead of substituting the fallback. Validate the logout nonce before destroying the session and return a controlled HTTP 403 for an invalid or stale nonce. Never treat the boolean return from `wp_safe_redirect()` as sufficient proof that a `Location` header can be emitted: check `headers_sent()` before dispatch and again before taking the success exit, because WordPress can return `true` after PHP has already committed output. A rejected redirect or committed-header state must never become a blank HTTP 200: render a controlled fallback with a validated same-site continuation link and record only bounded `auth.redirect_failed` codes/status—never the URL, nonce, cookie, identifier, token, source path, or trace. WordPress declares `wp_die()` as non-returning; do not append unreachable termination statements that break static analysis.
- Cover both redirect failure modes: an explicit false return and a truthy return followed by committed headers. The latter regression may use a test-only namespaced `headers_sent()` seam that delegates to PHP by default and supplies only the bounded false/true sequence needed to model the race; production header state must remain unfilterable. Assert the controlled fallback and privacy-safe event in both cases.
- Treat a checkout opener as replaceable fragment content. On modal close, restore focus to the captured node only while it remains connected; otherwise resolve the equivalent live explicit-login/conflict opener and focus it after background inertness is removed. Keep the lifecycle token check so a rapid reopen invalidates the old restoration callback. Browser coverage must deliberately replace the opener during a pending request rather than relying on nondeterministic WooCommerce timing.
- Keep the standalone account page as one centered authentication card without a promotional/benefits pane. Every OTP step keeps the code field immediately followed by the primary verification action; show the resend cooldown as status text rather than a disabled control, reveal a text-style resend action only when available, and place alternate login methods after it. Render the server's safe delivery copy as text, isolate mixed-direction content, and provide an explicit edit action that returns to the identifier step while clearing OTP secrets. A segmented-code appearance must be a dynamically sized, `aria-hidden` visual layer over exactly one real `type="text"` field; derive its slots, guidance, and limit from `codeLength`, and retain numeric input mode, one-time-code autocomplete, paste, WebOTP, and exactly one exact-length autosubmit. Keep native `required` semantics and live field errors even when custom validation is active; focus the first invalid control after validation, but never autofocus an input on initial render or a workflow transition. Focus a non-input step heading on an intentional transition, make all non-loader content inert while busy, and route submit, resend, and alternate-method actions through one request lock. Use the explicit Yekan Bakh family and exact-case font assets, one accessible focus treatment, control boundaries with at least 3:1 non-text contrast, mixed-identifier `dir="auto"`, and safe-area padding with `viewport-fit=cover`. Keep the full-width store exit inside the card but visually tertiary, and do not duplicate it with a first-step header arrow. Center the logo independently of the back control, use the slightly larger desktop treatment without enlarging it on mobile, and keep the mobile header at the top while vertically centering the remaining account content in the available viewport. Consolidate the identifier and password instructions into their bold labels instead of duplicating description paragraphs; password controls are LTR with the visibility toggle on the right. The password-step OTP and recovery alternatives remain two equal-width, normal-weight, visibly underlined actions separated by a pipe. At the supported 320px minimum, reserve the complete 44px back-control target plus an 8px gap on both sides of the centered logo so password-step navigation cannot overlap the wordmark.
- Apply the same account-interface contract to the WooCommerce checkout modal without changing its authentication endpoints. Render the modal at the page footer, outside the checkout `<form>` and WooCommerce's replaceable order-review fragments; semantic login forms must never become nested checkout forms or disappear during `updated_checkout`. A generic `checkout_error` must never open Pinova: keep ordinary missing/invalid billing-phone errors inline and focus the invalid `billing_phone` control. Open the modal only from an explicit login action or the scoped existing-account conflict link emitted by Pinova. Implement it as a labelled modal dialog with Escape closing, trapped/restored focus, background inertness and scroll locking, heading focus instead of input autofocus, one request lock, inert task content, and complete secret/timer/step cleanup on close. Keep the close control operable while a request is pending; closing aborts the active request when supported, invalidates its request identity so a late response cannot mutate reopened or closed state, restores the checkout background and opener focus, and does not remove the normal bounded network timeout. Preserve the configured 4–6 digit OTP behavior, localized-digit normalization, paste, autofill/WebOTP, and exactly one exact-length autosubmit.
- Anchor the checkout close control directly to `.pinova-auth-card`, outside the header, loader, and inert task content. Keep its 44px target at the top-left card corner with safe-area-aware 12px insets, preserve the close handler and icon, and remove header-relative translation only from this control. Scope close-control rules and the modal back-control position under `.pinova-auth-modal`; do not rewrite shared standalone geometry or generic theme buttons. A theme rule such as `:is(.btn, .button, button, [type="submit"], [type="button"])` has the same specificity as a single class, so test both stylesheet orders and assert computed positioning, no logo/control overlap, logo centering, focus trapping/restoration, and pending-request dismissal. Keep both shared account asset revisions synchronized when this CSS changes. Browser geometry checks do not replace physical-mobile safe-area and keyboard acceptance.
- Synchronize modal keyboard tests with the actual focused step heading after opening or changing a step; visibility, arbitrary sleeps, and animation frames are not proof that the asynchronous focus transfer has completed. Do not schedule duplicate transitions to the already settled opening step or focus the heading from test code to manufacture success. Keep whole-test retries disabled and preserve all product assertions; assertion waiting for an observable state is required and is not a whole-test retry. Run `tools/check-modal-test-sensitivity.mjs` against the disposable loopback WordPress site: healthy repetitions must pass, and each isolated response-only mutation must fail the intended heading, forward/reverse focus-trap, or close/back-position assertion. A runner error, missing test, unrelated failure, whole-test timeout, skip, retry, or surviving mutant must fail the sensitivity gate; never treat it as proof of product-fault detection. An assertion failure because required focus never arrives is an intended fault when the raw assertion headline identifies that contract. Validate that raw headline, not marker text in adjacent source snippets in a formatted report. The 120-case geometry matrix selects presentation states; it is not 120 real logins or backend transactions. These targeted mutations do not imply complete plugin defect coverage.
- Treat canonical `wp-login.php` account blocking as a staged, opt-in gate. The private administrator route must remain testable while the gate is off. A computed fallback route is not sufficient to activate blocking: require an explicitly persisted valid slug and a successful private-route login by a `manage_options` native user to create a 30-minute, single-use arm bound to a keyed slug fingerprint, that User ID, and `PINOVA_VERSION`. Enabling consumes the arm and writes a durable activation record; runtime blocking requires the setting plus the matching activation record. Disabling or changing the slug clears both activation and any outstanding arm, so another private login is required. Restrict private-route authentication and password reset to configured native-only roles, route public core login/register/lost-password helpers to Pinova using the public home URL, and rewrite only native administrator reset/recovery emails to the private route. Preserve the core `postpass`, nonce-protected `logout`, keyed `confirmaction`, administrator-email confirmation, and nonce-protected Recovery Mode exit handlers because they do not authenticate or recover an account; ensure their generated continuation/exit URLs stay on a working core/private handler. WordPress adds `confirm_admin_email` only after calling `wp_login_url()`, so test that real construction order on the private route; on an already-running canonical confirmation screen, preserve its continuation only for a logged-in user with `manage_options`, and never reveal the private slug to a logged-out request. Encode a nested return URL exactly once before passing it to `add_query_arg()`; WordPress does not encode newly assigned values there, and one request-query decode must restore the exact destination. Preserve `wp_login_url(..., true)` by carrying `reauth=1` to Pinova for public roles, clearing their existing authentication cookie/current user before rendering its form, and routing native-only roles through the private core pipeline. Keep `PINOVA_BLOCK_NATIVE_LOGIN=false` as an emergency recovery override. Log only bounded arming and gate-state changes with IDs/codes; never log canonical-path probes, raw slugs, route URLs, arm material, or slug fingerprints, and never print the private route in public account markup or REST output.
- The shared browser REST helper must return valid non-2xx Pinova/WordPress JSON responses to its callers instead of replacing them with a transport error. Prefer the field-specific WordPress validation message, preserve HTTP status, `Retry-After`, and Pinova correlation metadata, and show a generic helper-level notification only for network or malformed responses. Do not emit a duplicate notification from both the helper and its caller.
- Role allowlists must be revalidated after filters. A filter cannot admit roles with administrative, user-management, plugin-management, WooCommerce-management, or order-edit capabilities.
- Legacy upgrade methods are additive/no-op against WordPress core tables. Do not alter/drop core columns or indexes, rewrite core identity data, or add foreign keys to core tables.
- Spreadsheet formatting must stay within populated ranges. Never style whole worksheet columns such as `A:Z`, because PhpSpreadsheet materializes millions of cells and can exhaust PHP memory even for a tiny export.
- A `pinova_blocks` row with `blocked_until = NULL` is permanent. Expired cleanup must leave permanent blocks intact.
- Blocked List writes are type-authoritative: accept only `mobile`, `email`, `username`, or `ip`, normalize by that selected type before persistence and lookup, and never allow a manual request to convert or delete a system-managed block. Recheck both the client IP and identifier during OTP verification so a block added after code issuance still prevents authentication and user creation.
- Git source checkouts do not track `vendor/`; recreate PHP dependencies from `composer.lock` with `composer install`, and recreate JavaScript dependencies from `package-lock.json` with `npm ci --ignore-scripts`. Release ZIPs require the repository-pinned Composer 2.10.3. `tools/build.sh` must fail on a different Composer version, export `TZ=UTC`, and normalize staged directories/files to `0755`/`0644`, because Composer-generated autoload formatting, ZIP DOS timestamps, and checkout umasks otherwise vary across build hosts.
- After publishing and independently verifying a pre-release, record the exact CI runs, tag object and target, Release identity and immutability, asset digests, attestation results, fresh-download checks, predecessor-package diff, and any post-publication blocker in a separate documentation-only evidence change. Keep the installed baseline distinct from the newest published candidate, and never let evidence recording imply authorization for staging, production installation, settings changes, or native-login gate activation.
- Release evidence must identify each cited Quality run's GitHub event and exact head SHA. In a multi-commit PR, use the exact-head `pull_request` run for the complete base-to-head Skill synchronization decision; a branch `push` run may evaluate only its configured push base and must be classified separately rather than silently presented as the PR gate.
- Keep current status separate from historical evidence. An API asset digest is not an independent redownload, a synthetic PR merge is not a merge into the default branch, and an old green run does not certify a later documentation commit. A green and immutable release can still be superseded when later review proves a product defect; preserve it, document the blocker, and use a new candidate instead of altering its tag or assets. Store a small nonsensitive evidence summary under `.agents/reviews/`; browser artifacts have bounded retention. Never commit raw traces, credentials, or private host coordinates as a substitute.
- Root `CHANGELOG.md` is the complete release history, while the WordPress.org `readme.txt` Changelog section carries only the current release to stay below the directory size limit. Keep the current version and entry text identical in both files, update both together, and run `php tools/check-changelog-sync.php`; CI must reject drift. Keep the repository-only Markdown history out of the installable ZIP.
- A version bump requires a matching `Version::update_XYZ()` method, even when no schema changes are needed, so the installed-version option advances and the upgrader does not repeat on every request.
- Database lifecycle uses `pinova_db_schema_version`, not a file sentinel. Activation and ordinary startup share the same idempotent, retryable coordinator before runtime services boot. Schema creation uses WordPress `dbDelta()` and must not require PDO/Eloquent during plugin activation; runtime Eloquent initialization remains a separate bootstrap invariant. Stamp the current plugin version only when no Pinova table, option, or version metadata exists; an existing installation with missing version metadata must run legacy migrations from the baseline. Deactivation clears Pinova schedules; uninstall preserves data unless the administrator explicitly enabled `pinova_delete_data_on_uninstall`, and even opt-in operational purge preserves `pinova_mobile` user metadata. A failed purge stops before options are deleted so the failure remains retryable.
- Integration tests must load the configured WooCommerce checkout before Pinova and exercise real WooCommerce classes. Forward `PINOVA_TEST_HPOS=yes|no` into `tests-cli`; the bootstrap must set the HPOS option in the PHPUnit database, not the separate development database. The disposable `tests-cli` container also needs `pdo_mysql` because Pinova's Illuminate database layer uses PDO even when WordPress itself uses mysqli. When installing it through in-container `sudo`, pass `PHP_INI_DIR=/usr/local/etc/php` explicitly because sudo does not preserve that image environment variable.
- Browser fixtures that call real Pinova REST authentication must explicitly bootstrap the plugin tables in their disposable wp-env database before the first request. Merely mounting Pinova as an active wp-env plugin does not prove its activation-task sentinel has run, and a missing `pinova_blocks` table turns the identifier check into a transport error instead of exercising login or logout. Shopper-facing fixtures must also set both WooCommerce coming-soon options to `no`; fresh WooCommerce installs can otherwise replace checkout with the launch page for guest contexts while a preceding authenticated check appears healthy. Obtain ordinary-user logout links from the real WooCommerce account page because WooCommerce can redirect non-administrators away from `wp-admin`.
- Give every GitHub Actions wp-env job a run-specific Compose project and `WP_ENV_HOME`. At job-level `env`, use a run-specific absolute `/tmp` path built from the `github` context; the `runner` context is not available there and makes the workflow invalid before any job starts. Use `localhost` consistently in both the Playwright configuration fallback and the CI base-URL override so module scripts and fonts stay on wp-env's generated WordPress origin. The browser job uses `bash tools/cleanup-browser-env.sh` rather than relying on a version-specific force flag. That script must validate the exact run identity, project, and work directory before scoped Compose teardown, preserve shared images, and verify no run-owned containers, volumes, or networks remain. Cleanup errors must fail the job rather than being hidden by `continue-on-error`. This script is CI-only, not a desktop cleanup procedure.
- Treat the repository's PHP 8.1 PHPCS job as release-blocking. WordPress Yoda-condition checks apply to every comparison in a compound expression, including strict comparisons between a getter result and a local value; correct every reported clause before publishing another head.
- Repository quality gates include JavaScript syntax lint, WordPress Plugin Check, readme/metadata validation, actionlint, and ShellCheck. A PHPCS scope expansion must land in the same focused change that makes every added first-party path compliant; never claim coverage before the gate enforces it, and never narrow an already-enforced scope to hide violations. Keep active gates in the aggregate required check; exclusions are limited to dependencies and generated artifacts.
- When an integration test directly seeds a legacy autoloaded option through `$wpdb` to bypass the current sanitizer, invalidate both the option's individual object-cache key and the `alloptions` cache before reading it back. Otherwise the test may assert against the prior sanitized value instead of the simulated database state.
- Do not instantiate `WC_Checkout` from the early `woocommerce_loaded` bootstrap merely to read whether registration is required. Derive the same filtered option value without constructing checkout, and keep the integration regression assertion that Pinova load does not trigger WooCommerce just-in-time translation warnings.
- Checkout phone validation must consume the already-sanitized data and `WP_Error` supplied by `woocommerce_after_checkout_validation`. Never call `WC()->checkout()->get_posted_data()` from `woocommerce_checkout_process`: WooCommerce parses the payload immediately after that action, and doing it inside the action re-enters all checkout-field filters early and can produce repeated lifecycle warnings from extensions.
- Never log raw identifiers, OTPs, passwords, reset keys, tokens, or full proxy headers. Use IDs, masked values, event types, and correlation IDs.
- Runtime logs use stable event codes and the PSR-3 levels through `Pinova\Logging\Logger`. Context is deny-by-default: add a documented allowlist key or keyed fingerprint instead of arbitrary prose. Never persist exception messages or traces. Debug requires an expiring diagnostic window; normal retention is bounded and cleanup is batched.
- Package build identity is injected deterministically during release packaging and validated before logs use it; source checkouts must not invent a release tag or commit. Settings audit includes defined first-party SMS provider options and records only changed key names, an authorized actor, and outcome—never setting values. Incident exports require administrator capability and nonce, bounded UTC range/rows/bytes, and redaction even for historical rows. Viewer health must not imply database write success from a read-only probe or claim cross-request fallback detection.
- WordPress privacy export includes only Pinova-owned mobile/profile data and non-sensitive audit facts; it never exports OTP records, credentials, tokens, fingerprints, or arbitrary log context. Email fingerprints are trimmed and lowercased centrally before HMAC creation. Approved erasure derives email ownership from the matched account's stored address plus normalized request variants; a confirmed address without a WordPress account may erase only matching unowned pre-account records. Erasure removes matching temporary OTP records, clears User ID from that user's log rows and keyed fingerprints only from unowned pre-account rows, and deletes the physical `pinova_mobile` value only after every identifier-dependent log batch succeeds. A failed account, physical-mobile, or audit-record read must stop before dependent writes. Export read failures return a bounded `WP_Error` so WordPress aborts instead of advancing past the failed page; erasure read failures report retained data and an incomplete operation so WordPress can retry them. Never anonymize another user's owned log row merely because it contains the same fingerprint. When old HMAC input or a rotated auth salt makes an exact fingerprint unrecoverable, an approved erasure may clear fingerprints from unowned rows explicitly classified with the erased identifier type while preserving event facts and every row owned by a User ID. For legacy pre-account records only, `created_by=pinova` plus a mobile-shaped account login establishes erasure ownership but never export ownership. Any erasure write failure must report retained data and an incomplete operation so WordPress can retry it.
- Logging is permanent plugin infrastructure, but individual records are temporary operational data. A logging failure must never interrupt login, OTP, REST, export, or another user request. Repeated attacker-controlled failures must be transition-logged or otherwise throttled to prevent log amplification.
- Correlation must cover WordPress-generated Pinova REST errors, not only application envelopes; unrelated namespaces remain untouched. User/admin error references come only from validated server response headers, never a client-generated fallback. Known-record OTP verification metadata must use the identifier HMAC, never an OTP-code fingerprint. Logout rejection and password-reset observations use the finite atomic throttle in the logging reference and must never bypass severity configuration or become authentication access decisions.
- Pinova's structured event table does not replace WordPress, WooCommerce, PHP, or web-server diagnostics. A clean Pinova event stream does not rule out lifecycle/deprecation warnings. Inspect those streams during compatibility investigations; do not mirror every global `doing_it_wrong_run` event into persistent Pinova logs because unrelated extensions and repeated public requests can amplify them.
- Treat the authorized administrator SMS test as a bounded audit action: its success and failure events must persist even when the configured minimum level is `error`. Catch `Throwable` at this REST boundary, return a generic message for non-provider PHP errors, and never persist the throwable message or trace.
- Trust only `REMOTE_ADDR` by default. Proxy headers require an immediate peer in an explicitly configured trusted CIDR.

## Workflows

### Review or diagnose

- Keep the task read-only unless the user explicitly asks for a fix.
- Establish claims with source, tests, logs, or a disposable WordPress environment. Separate plugin defects from server rewrites, provider failures, or unsupported WordPress/WooCommerce pairs.
- Report affected version, identifier type, role policy, login method, HPOS mode, and whether failure happens before or after WordPress hooks.

### Change code

1. Branch from the exact affected ref in a separate worktree; do not develop in `<production-wordpress-root>/wp-content/plugins/pinova`, and do not hard-code the real host path in public documentation.
2. Add a regression test when practical. Authentication, identifier, database, exports, proxy, redirect, and WooCommerce changes require integration coverage. Checkout validation coverage must prove the early process action does not parse the complete payload and that the later validated-data hook accepts normalized mobile input while rejecting invalid or non-string input through WooCommerce's error container.
3. Make the smallest coherent change and preserve the REST envelope `{success,message,data}` where compatibility requires it.
4. For mobile profile changes, store the normalized value in physical `pinova_mobile` meta, validate ownership/conflicts, and keep `user_login` immutable.
5. For Blocked List changes, test every supported identifier type, permanent/temporary expiry, system-block immutability, capability denial, filtered pagination, current-page refresh after add/delete, privacy-safe logs, and both issuance-time and verification-time authentication denial.
6. For native-login routing changes, verify that the private route keeps the core login form/action flow and security hooks, accepts only native-only roles, preserves upstream password-reset `WP_Error` denials, account actions on direct `wp-login.php` return 404 only after opt-in, and exact non-authentication actions preserve password-protected posts, logout links, privacy confirmation, administrator-email confirmation, and Recovery Mode exit. Exercise the real administrator-email URL order (`wp_login_url()` first, `confirm_admin_email` second), plus a logged-out canonical request that must not receive the private slug. Public core login/register/recovery helpers must resolve from `home_url()` and restore their exact return targets after one request-query decode. Force-reauthentication URLs retain `reauth=1`; public-role sessions are cleared before the Pinova form is rendered, while native-only roles use the private core route. Native administrator reset/recovery emails use the private route even when core lives below the public home URL, the public Pinova account page exposes neither native route, and the emergency constant restores canonical access. At `login_init`, authorize only WordPress's already-normalized global action because query keys such as `key` and `checkemail` can override the raw request action; match allowed actions exactly so case or whitespace variants cannot fall through to login. Keep integration assertions origin-agnostic by comparing generated private URLs with `NativeLoginGate::url()` and the expected route path because wp-env may filter the test origin.
7. For logging changes, update the event catalogue and privacy allowlist in `references/logging.md`, add a no-secret regression test, and exercise schema upgrade plus retention cleanup.
8. Run targeted checks and the proportional suite in the quality reference.
9. Update public documentation plus both `CHANGELOG.md` and the `readme.txt` Changelog section when behavior changes.
10. Update this skill or a routed reference when the change modifies an invariant, interface contract, command, integration boundary, or development/release procedure. Do not make ceremonial edits for ordinary implementation changes.
11. Run `php tools/check-ai-governance.php` and `bash .agents/skills/pinova-development/scripts/check-skill-sync.sh --working-tree` before handoff. The checks verify structure and changed-file participation; separately review semantic correctness.

### Migrate or merge identities

- Identity-table migration and multi-account merge are 1.3 features, not part of the 1.2.3 hotfix. Do not backport schema or automatic merge behavior casually.
- Use a fresh staging copy, audit, and dry-run before apply. Require an immediate full database backup and explicit canonical User ID for every multi-account merge.
- Block apply on Multisite. Unsupported ownership systems require a preflight stop until an adapter exists.
- Discovery/audit must not write. Apply must be additive, batched, idempotent, resumable, and journaled, with maintenance always cleared in a `finally` path.

### Package or release

- Read the quality/release reference before changing versions, tags, ZIPs, workflows, or GitHub Releases.
- Record every durable change intended for a Pinova test version through a named GitHub branch, reviewable commits, a pull request, required CI, and merge. Never describe local implementation as a completed phase or an installable version while that GitHub record is missing. If GitHub mutation has not been authorized, stop at the local candidate and report publication as an explicit incomplete gate.
- Treat a version as ready for installation only after the GitHub Release API reports native `immutable: true`, the Release contains its installable ZIP, ZIP checksum, SPDX SBOM, and SBOM checksum, all assets have been downloaded again, and their GitHub attestations, SBOM attestation, and local integrity checks pass. Never direct the user to install a worktree-local ZIP.
- Release candidates remain pre-releases until staging and canary gates pass. Stable/latest publication needs explicit authorization.
- For a release that changes or can block an authentication route, keep the blocking gate disabled by default and treat package installation and gate activation as separately authorized operations. Before activation, preserve an authenticated administrator session, document the emergency override and rollback, and verify the private administrator route in a clean session together with security-plugin/2FA hooks and every protected core action the gate intentionally exempts.
- For an account-interface release, source assertions and packaged-file checks prove structural invariants, not visual acceptance. Before production use, exercise the published ZIP at agreed desktop and mobile widths, including identifier editing, configured code length, paste/autofill and autosubmit, resend transition, keyboard focus, error/success states, and horizontal overflow. Keep this staging/canary acceptance separate from publication, state explicitly in the release evidence whether live visual acceptance remains outstanding, and record any defect in a new RC rather than changing an immutable release.
- Build twice from the exact tag, compare SHA-256, publish the installable ZIP with its checksummed SPDX SBOM, attest the ZIP with that SBOM, download every asset again, and verify checksums, attestations, ZIP integrity, and top-level `pinova/`.
- Run `php tools/check-changelog-sync.php` before selecting a release commit; a release with missing, reordered, or divergent history is not ready.
- Automated pre-release publication starts only after a successful `Quality` run on an exact `publish/vX.Y.Z-rcN` branch. The completed run dispatches the publisher on that same branch ref so the publisher's workflow identity and attestation source digest are bound to the release SHA; the publisher independently requires the named `Quality` run, branch, repository, result, and `GITHUB_SHA` to match before any publication step, and attestation verification must require that exact source digest. It uses only the job-scoped `GITHUB_TOKEN`; neither an Administration-scoped secret nor a repository Ruleset is a publication prerequisite. The repository owner must confirm native Release Immutability is enabled before the publish branch is created because the workflow cannot read that administrative setting before creating the tag. The publisher validates that the commit is reachable from `main` and matches the plugin version, creates an annotated tag, builds twice, generates a deterministic SPDX SBOM from the staged production tree, attests the ZIP with that SBOM, and uses an explicit draft-upload-publish sequence for the ZIP, ZIP checksum, SBOM, and SBOM checksum. It then requires the published Release API to report native `immutable: true`, verifies release-asset and SBOM attestations, and redownloads every published asset. Release notes created before that post-publication check must describe immutability as a required gate and make installation conditional on successful workflow completion; they must not claim the gate has already passed. A rerun may resume an unpublished draft only after its server-supplied author is `github-actions[bot]` and its name, target SHA, complete publisher-marked body, and allowed asset names match this exact release; it reuploads the reproducible assets before publication, never deletes or changes an unknown draft, preserves any published immutable Release, and refuses a published mutable one. If the post-publication immutability check fails, retain that tag and Release unchanged and use a new RC tag after correcting the repository setting. Never create the publish branch until the intended commit is already reviewed and green on `main`.
- After publication, record the immutable tag target, Release state, asset digests, verification evidence, and next operational boundary in repository guidance through a follow-up documentation PR. Keep the provenance chain auditable by naming the implementation PR and CI, merged `main` SHA and CI, publish-branch CI, publisher workflow, annotated tag object and target, Release ID/state, asset digests, attestation result, and independent redownload result separately. Do not edit the immutable Release or move its tag merely to synchronize prose.
- GitHub publication never authorizes installation, configuration changes, or database writes on the production site.

## Documentation governance gate

The repository enforces durable instruction ownership with [`scripts/check-skill-sync.sh`](scripts/check-skill-sync.sh) and `tools/check-ai-governance.php`:

- update this entrypoint only for decision-changing guidance or routing;
- place stable detailed procedures in the relevant reference;
- keep repository-wide rules in root `AGENTS.md` and do not duplicate them in provider adapters;
- keep operational snapshots and exact evidence under `.agents/reviews/` rather than durable entrypoints;
- update Persian `README.md` and WordPress `readme.txt` when stable public behavior, requirements, installation, privacy, or operations change;
- update changelogs only for released behavior or an explicitly prepared release, and keep both release-history views synchronized.

Do not use a date-only or whitespace-only edit to satisfy the gate.

## Completion gate

Finish only when the requested behavior is evidenced or implemented, required checks pass (or failures are accurately classified), guidance is synchronized, requested artifacts are reproducible, and no production or external state changed outside the user-authorized scope. When the requested outcome is a version ready for installation, completion additionally requires the GitHub branch/PR/CI/merge record, a GitHub pre-release or release whose API reports `immutable: true`, successful GitHub attestation checks, and successful redownload verification of its ZIP, ZIP checksum, SBOM, and SBOM checksum. Handoff must name branch, PR, merge commit, tag, Release URL, asset checksums, checks, remaining risk, and the separately authorized installation step.
