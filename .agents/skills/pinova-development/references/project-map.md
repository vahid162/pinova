# Pinova project map

Read this reference when locating code, reviewing authentication or identifiers, changing persistence, or assessing integration impact.

## Entry points and modules

- `pinova.php`: metadata, constants, bootstrap, integrations, and HPOS declaration.
- `src/API/`: REST controllers and response envelope.
- `src/Services/`: OTP, users, validation, rate limiting, firewall, SMS, channels, and API orchestration.
- `src/Objects/`: normalized request identifiers and mobile handling.
- `src/Integrations/Wordpress/`: profiles, users list, export authorization, Excel, VCF, WordPress privacy exporters/erasers, policy text, and the staged native-login gate.
- `src/Integrations/Woocommerce/`: login/account/checkout and constrained customer creation.
- `src/Helpers/IP.php`: client-address and trusted-proxy handling.
- `src/Logging/`: PSR-3 logger, safe-context allowlist, database handler, retention repository, and fallback handling.
- `src/Admin/Logs.php`: capability-protected operational log viewer and manual clear action.
- `src/Install.php`, `src/Version.php`, and `utils/`: additive schema, upgrades, settings, and compatibility helpers.
- `templates/` and `assets/`: login interface.
- `tests/`: unit, plugin-load, and security integration coverage.
- `tests/browser/account-ui.spec.mjs`: real disposable WordPress browser acceptance, including modal control geometry and keyboard behavior.
- `tools/check-modal-test-sensitivity.mjs` and `tests/js/modal-test-sensitivity.test.mjs`: loopback-only response mutations and strict report classification; no runtime plugin edits.
- `tools/cleanup-browser-env.sh` and `tests/js/browser-cleanup.test.mjs`: verified cleanup restricted to the current GitHub browser job, with fake-Docker unit coverage.
- `.agents/reviews/`: immutable historical evidence; never treat a record there as a live release or deployment pointer.

Identity-table resolver, migration, merge, rollback, and WP-CLI code live only on the separate 1.3 development line until explicitly merged. Do not document those features as shipped by 1.2.3.

## Identifier behavior in 1.2.3

`UserService::match()` resolves email through WordPress, username through WordPress, and mobile through legacy `user_login` plus configured metadata aliases. Queries use prepared placeholders.

A valid physical `pinova_mobile` value is an explicit login-mobile override. It is checked before legacy values when displaying a user's mobile. If an account later stores a different explicit override, the old value remains unchanged in a mobile-shaped WordPress username or legacy metadata but no longer authenticates as that user's Pinova mobile alias.

The shared physical reader selects at most two distinct binary values. Byte-identical duplicates are accepted without deletion; conflicting rows and database failures stop resolution before OTP consumption, proof changes, or privacy erasure. Do not reintroduce a first-row reader in security-sensitive consumers.

Resolution returns a User ID only when the candidate is unambiguous. Multiple legacy accounts matching one mobile return no user and fire `pinova/identity_conflict_detected`. Resolving that conflict and merging ownership is deferred to the reviewed 1.3 workflow.

## Data tables and queued delivery

The Illuminate initializer parses `DB_HOST` through WordPress's `wpdb::parse_db_host()`, passing host, port, and Unix socket separately and preserving WordPress's IPv6/mysqlnd convention. Keep eager request initialization and resolver reuse; never log connection credentials or configuration on parse failure.

Public OTP initiation stores an AES-256-GCM-authenticated, short-lived delivery payload in the rate-limit reservation row as reserved ciphertext. Only after signed response preparation and successful scheduling is it durably acknowledged as ready ciphertext. It schedules `pinova_otp_delivery` for eligible and decoy identifiers alike. The REST callback never resolves the account or calls a provider before returning its uniform response. The delivery callback atomically claims the flow while retaining authenticated ciphertext behind a claim token and a database-connection lock, then resolves account policy and sends only when eligible and before the signed deadline. A crashed worker releases its lock; a later claim can retry after the bounded lease. An existing OTP with unknown provider outcome is kept valid and is not resent; the reservation is retired so a later initiation can open a fresh flow. Verification retires a completed reservation, or cancels an in-flight claim until its worker exits. Repeated initiation otherwise reuses the same flow without resending an already-created OTP. A functioning WordPress cron runner and OpenSSL are required; a queue or scheduling failure returns a generic error before account lookup. Approved privacy erasure cancels matching claimed work and remains incomplete until its worker exits or a lock-free stale claim is retired.

`OTPImmediateDelivery` provides optional same-process dispatch only when `PINOVA_OTP_IMMEDIATE_DELIVERY` is strictly `true`. Successful originating APIs arm their own scheduled, acknowledged flow. Actual final JSON, response identity/status/headers, native empty initial buffers, late shutdown output and fatal state must pass before successful `fastcgi_finish_request()`. This is server-side completion, not browser packet-arrival proof. Preserve WordPress's priority-one native buffer flush through the request-scoped wrapper; unsupported or changed output retains cron. Independent cron already accepts prepared responses and may race before flush; do not change that protocol incidentally.

After completion, immediate delivery requires Linux `MemAvailable` of at least 1 GiB and one-minute load below 3; unknown headroom defers. Two nonblocking site-scoped connection-owned locks cap admitted fast work. Recheck original connection identity, both slot/flow lock ownership, active claim and expiry at the final provider boundary so observed reconnects fail closed. Only exact first-party MeliPayamak/MaxSMS/PanelChi gateways and native Bale/voice HTTP paths qualify; email, external gateways/subclasses and custom Bale functions retain cron. The eight-second aggregate HTTP deadline is request-local and positive per-call timeouts are clamped to remaining time; it is not a hard PHP lifetime bound. Before any provider attempt, deferral may restore only the exact acknowledged ciphertext/timestamp under its original claim. After any attempt, unknown acceptance never restores readiness or automatically resends. Disable the flag to roll back admission and let in-flight native work finish; leave the durable runner and signed expiry intact.

The FPM worker must be able to read the bounded `/proc/meminfo` observation under the site's file policy. An `open_basedir` denial or unreadable memory leaves delivery on cron. Pinova never expands file access automatically: a site allowlist change requires explicit operator approval for the exact file while preserving existing entries. Exact-file permission keeps neighboring procfs files outside that allowance. The isolated full-stack resource fixture applies the same restricted policy to both OFF and ON measurements; native response-boundary cases separately prove exact-file access and safe non-dispatch when memory remains blocked.

The single-site WP-CLI command `wp --path=<site> pinova otp run` uses native ready-cron enumeration and unscheduling, dispatching due one-shot `pinova_otp_delivery` events with one valid opaque flow argument. It also recovers acknowledged live reservations whose one-shot job disappeared, using the same claim and provider safeguards. Legacy raw ciphertext requires its scheduled callback; unacknowledged reservations and released provider failures are never recovered automatically. A native one-minute Pinova watchdog uses the same bounded runner when automatic cron is available and is cleared on deactivation. It leaves foreign, future, recurring and malformed events unchanged, rejects missing callbacks or unscheduling failures, and processes at most three jobs, starting new jobs only during the first 20 seconds. It retains the existing claim/deadline/provider boundary; a job count does not establish provider acceptance or recipient receipt. The external host runner must acquire the site's shared cron lock, run frequently enough for the signed deadline, and bound resources/runtime. Do not change disabled automatic cron or server schedules through the plugin.

`OTPQueueStore` owns reservation persistence, authenticated encryption, acknowledgement, claim leases and connection locks. `RateLimitService` retains the existing public queue methods as delegates for callers and hooks; its rate-limit buckets remain separate. Preserve stored marker/ciphertext formats, lock names, update ordering and deadlines when editing this boundary. The concurrency regression starts independent PHP/wpdb workers on the disposable PHPUnit database, passes connection settings only through stdin, and cleans only its own queue rows.

Queued provider authorization is scoped to the exact original connection, flow lock and claim token for cron as well as immediate delivery; immediate work also retains its fast-slot guard. Internal terminal decisions distinguish an unavailable ownership read from known cancellation/expiry instead of collapsing both into the public bool compatibility result. Before any provider handoff, unavailability propagates `OTPDeliveryDeferredException`; only a still-owning worker may restore the exact READY reservation, while lost/unknown ownership cannot consume it. Preserve a prior accepted or uncertain provider outcome and never automatically resend it. An explicit false result retains deliberate retry behavior. The final compound ownership read and request-local attempt witness must not be replaced by diagnostic state or by a retry/readback after an unknown SQL result.

OTP instrumentation buffers bounded in-memory facts while claims or immediate leases may be held, including lock acquisition before registration. Only positively observed release permits diagnostic flush. Queue health and OTP cleanup health are separate read-only snapshots; see [the logging contract](logging.md#current-otp-health) for finite keys, nullable failure semantics and timing precision.

- `pinova_otp`: OTP attempts, channels, expiry, and verification.
- `pinova_blocks`: temporary or permanent blocked identifiers.
- `pinova_rate_limits`: atomic hashed rate-limit buckets and short-lived durable decoy-flow reservations; expired rows are removed by the daily cleanup.
- `pinova_logs` (1.2.4+): temporary structured operational events, correlation IDs, optional User IDs, and allowlisted JSON context.

The additive flow schema gives `pinova_otp` and `pinova_logs` nullable indexed `flow_id` columns. New OTP records generate the ID server-side and bind it to signed JWT state; existing rows remain valid with null. The database migration coordinator advances its per-site option only after both columns and indexes exist, so an interrupted upgrade can retry and previous code ignores the added fields.

New public OTP state tokens contain only an opaque, server-generated `flow_id`; the database record ID and account classification are not exposed in the token. Decoy states use the same signed shape and atomically reuse a durable rate-limit-table reservation until expiry, while signed legacy `otp_id` states remain valid until expiry. Public OTP-initiation responses use the same status and delivery copy for eligible, native-only, unknown, and delivery-failure cases; do not reintroduce channel- or account-specific details. A rate-limit or decoy-state storage failure rejects the request before identity lookup. Verification conditionally claims a still-live OTP record before authentication and increments failed attempts atomically, so a stale concurrent read cannot accept the same code twice.

Schema changes must be additive and `dbDelta()` compatible. Never alter/drop columns or indexes in `wp_users` or other core tables.

Lifecycle setup is database-coordinated through `pinova_db_schema_version`; runtime code never writes activation sentinels into the plugin directory. Activation and normal startup call the same idempotent migration coordinator before services boot. Initial table creation uses WordPress `dbDelta()` so activation does not depend on PDO/Eloquent being available before the host finishes provisioning PHP extensions. Only an installation with no Pinova tables, options, or version metadata is stamped at the current version; an existing installation whose version option is missing runs legacy migrations from the baseline. A failed migration leaves the version unchanged for retry and keeps Pinova runtime integrations unloaded so native WordPress access remains available. Network-wide activation is unsupported and must fail with an administrator-facing explanation.

WordPress privacy export returns only the Pinova-owned mobile profile value and non-sensitive audit facts (event, UTC time, and correlation ID). It never exports OTP rows, credentials, tokens, keyed fingerprints, or arbitrary log context. Email fingerprints are trimmed and lowercased centrally before HMAC creation. Approved erasure derives email ownership from the matched account's stored address plus normalized request variants; a confirmed address without a WordPress account may erase only matching unowned pre-account records. Erasure removes matching temporary OTP records, clears personal linkage from rows owned by the User ID and unowned pre-account rows carrying the keyed email/mobile fingerprint, and deletes physical `pinova_mobile` metadata only after every identifier-dependent log batch succeeds. Failed account, physical-mobile, and audit-record reads keep the operation incomplete before dependent writes. A matching fingerprint never authorizes anonymizing a log row owned by another User ID. For pre-canonicalization email HMACs whose original casing is unrecoverable, a confirmed email erasure may clear fingerprints from all unowned rows explicitly classified as email while preserving event facts and every row owned by a User ID. For legacy pre-account records, `created_by=pinova` plus a mobile-shaped account login is an erasure-only ownership signal and is never exported as Pinova profile data. A failed OTP, metadata, or log write reports retained data and leaves the operation incomplete for retry.

Deactivation clears every hook returned by `Install::scheduled_hooks()`. Uninstall preserves data unless `pinova_delete_data_on_uninstall` is explicitly enabled. Opt-in purge removes Pinova tables, options, transients, and schedules while preserving account identity metadata such as `pinova_mobile`. It deletes the schema-version checkpoint before dropping tables, keeps the purge opt-in until all other deletions succeed, and fails on an option-read/delete error. If interrupted, normal startup re-runs the idempotent installer; a table-removal failure aborts before the remaining options are deleted so the administrator can retry safely.

Blocked List writes require an authoritative `blocked_type`: `mobile`, `email`, `username`, or `ip`. REST writes validate the selected type, persist the canonical identifier for that type, store `NULL` for a permanent block, and keep system-managed rows immutable through manual add/delete operations. The current table stores the canonical identifier rather than a separate type column, so response resources derive `identifier_type` from the stored value. List filters return a stable `{users:[{id,name}]}` shape and server pagination metadata. Authentication checks the normalized identifier and client IP before OTP issuance and checks them again during OTP verification; therefore adding a block after issuing a code must still prevent verification, session creation, and user creation.

The 1.2.x Eloquent models depend on the connection initializer in `utils/class-database.php`. Composer includes that file in `autoload.files`, not only in the classmap: a classmap makes the class discoverable but does not execute the bottom-of-file initializer on a fresh request. Because a CLI/test process may load Composer before WordPress exists, `pinova.php` also performs an idempotent resolver check and explicitly initializes the connection after WordPress loads. Integration bootstrap checks the resolver before any installer helper can conceal this failure.

## Security boundaries

- Exports require `list_users`, nonce validation, safe strings, VCF escaping, batching, and XLSX row limits.
- WooCommerce customer creation accepts only allowed billing/shipping input and forces role `customer`.
- Redirects require `wp_validate_redirect()` and the allowed-host policy; an omitted or empty return target is replaced explicitly with the safe role-aware/site fallback because WordPress otherwise preserves the empty location. Public login/logout routes derive from `home_url()`, and a nested return URL is encoded exactly once before `add_query_arg()` so a single request-query decode restores the exact destination. Pinova logout URLs use canonical `/logout/`; an invalid/stale nonce terminates with HTTP 403 before session destruction, while a rejected safe redirect after a completed logout terminates with an HTTP 503 page containing only a validated same-site continuation link instead of a blank 200. A core force-reauthentication URL retains `reauth=1`: public-role sessions are cleared before Pinova renders, while native-only users continue through the private core handler.
- Public password/forgot/OTP responses do not expose account existence or native-only role membership.
- OTP records are purpose-bound at reuse and verification: ordinary OTP login accepts only `login`/`register`, password recovery accepts only `forget`, and a mismatch fails before verification, account/session creation, or reset-key issuance. Concurrent purpose-specific codes remain independently valid only in their own flows. Email delivery carries a purpose-specific subject, explanation, instruction, and footer and is addressed only to the normalized user email; Pinova does not copy OTPs to an administrator.
- Native administrator password/2FA login remains available through the private Pinova administrator route, which internally executes `wp-login.php` and its core/security-plugin hooks. Canonical account actions can return 404 only when an explicitly persisted private slug, the blocking setting, and a matching durable activation record are all present. A successful private-route login by a `manage_options` native user creates a 30-minute single-use arm bound to the slug HMAC, User ID, and plugin version; enabling consumes it, while disabling or changing the slug invalidates both arm and activation. Exact core handlers remain available for password-protected posts, nonce-protected logout, keyed privacy confirmation, administrator-email confirmation, and nonce-protected Recovery Mode exit. The private route remains testable before enablement, is derived from the public home URL even when WordPress core is installed in a subdirectory, and is never rendered by the public account template, REST output, or structured logs.
- Rate limits hash identifiers and return HTTP 429 with `Retry-After`.
- Active mobile, email, username, and IP blocks deny the corresponding public authentication path without exposing account existence. Block messages may identify the blocked input type but never disclose whether a WordPress account exists.
- Logs retain stable codes, keyed identifier fingerprints, and bounded context—not raw identifiers, secrets, exception messages, or traces. REST responses include `X-Pinova-Correlation-ID` for support correlation.
- Proxy chains are considered only behind trusted CIDRs.

## Client REST response contract

`assets/js/global.js` is shared by the full-page login, login modal, Blocked List administration, and WooCommerce customer-creation modal. For a valid JSON response it returns the existing server envelope and adds an `http` object containing the status, optional `Retry-After` values, and optional Pinova correlation ID. A non-2xx JSON response is normalized to `success: false`; standard WordPress argument-validation errors prefer their field-specific `data.params` message over the generic `rest_invalid_param` summary. Callers remain responsible for rendering those server messages. The helper itself shows a generic notification and rejects only when transport fails or the response is malformed, preventing duplicate notifications while preserving actionable blocked, OTP, and rate-limit failures. Public OTP delivery errors are deliberately not distinguished from decoy responses; operators use bounded server-side events for diagnosis.

`assets/js/pages/auth-state.js` creates fresh forms, OTP submission state, messages, and timers for each standalone or modal controller. Shared methods retain opaque signed state byte-for-byte. Keep request cancellation, modal focus/lifecycle and standalone history in their controllers. When the shared module changes, synchronize both import query revisions and the account asset suffix in the standalone template and WooCommerce loader.

WebOTP waits belong to an accepted current flow, with an AbortController and generation plus exact component/form/state/identifier checks. Capture the stable Alpine component root during initialization; invoking-element `$el` can point to a button detached by the next step. Start/restart only for an accepted flow, and invalidate on replacement, identifier edit, history, page hide, close and component destruction. A valid current credential arriving during ordinary verification failure is buffered until the request clears its fields; retain the rejected-code guard so it cannot automatically repeat, while explicit manual retry remains available. HTTP 429 ends the wait. Browser cancellation does not cancel server delivery or extend signed validity. Never send caught objects or credential contents to the console.

The Woodmart/Flatsome partial text-renders safe feedback and optional server reference, uses per-mount field/error IDs and labels, and scopes focus to its captured component. Its optional autofill observes the actual theme owner: native sidebar close, the owned Magnific content's configured before-close target, or the bounded two-owner Woodmart dropdown lifecycle. Dropdown class history and logical hover state must invalidate rapid close/reopen even during a visibility transition; computed visibility alone is insufficient. Bind only capability-verified APIs and remove only owned hooks. Missing optional lifecycle capabilities disable autofill while manual authentication stays usable. Adapter-HTML browser fixtures and mocked credential APIs do not establish full commercial-theme styling, physical phone behavior or message receipt.

For failed envelopes the client also provides `userMessage`, the sanitized explanation without its support reference; `message` retains the combined text for existing callers. Account interfaces render `userMessage` and the validated `http.correlationId` separately, with the reference in an LTR text node. Malformed responses with a validated server header expose `pinovaUserMessage` and `pinovaCorrelationId` alongside the legacy `pinovaMessage`; network-only failures never invent a reference. Clear the prior reference when an error changes or the workflow resets. OTP rejection copy gives a neutral retry/reissue action and must not disclose account existence, expiry, policy or the internal failure reason.

WooCommerce bootstrap runs early enough that constructing `WC()->checkout()` can trigger its text domain before WordPress permits just-in-time translation loading. The registration-required default mirrors WooCommerce's filtered `woocommerce_enable_guest_checkout` option without constructing checkout. Checkout phone validation runs on `woocommerce_after_checkout_validation`, consumes WooCommerce's already-sanitized data and `WP_Error`, and never reparses the complete payload from `woocommerce_checkout_process`.

## Standalone account UI contract

The full-page interface in `templates/login-form.php` is one centered authentication card; do not add a second promotional pane. Its OTP flows share one hierarchy: generic server delivery copy and edit action, code field with configured-length guidance, primary verification, resend availability, then any alternate login method. Delivery copy is text-bound rather than interpreted as HTML and mixed-direction content uses plaintext/bidirectional isolation. Editing the identifier returns to `authenticate` through the component state transition so short-lived OTP and reset secrets are cleared.

The resend countdown communicates availability only. While it runs, render plain status text without per-second live-region announcements; when it ends, replace that text with a touch-sized text action. Keep the OTP as one real `type="text"` field with numeric input mode and `autocomplete="one-time-code"`; segmented boxes are an `aria-hidden` visual layer whose count comes from `codeLength`, never separate inputs or a hard-coded digit count. Preserve paste, WebOTP, and exactly one exact-length autosubmit. Native required semantics and live field errors accompany custom validation; validation focuses the first invalid control, while initial render and normal workflow transitions never focus an input or open the mobile keyboard. Intentional transitions focus a non-input heading. One request lock covers submit, resend, and alternate methods, and all non-loader content is inert while a request is active. Explicit Yekan Bakh typography, exact-case font assets, one accessible focus treatment, 3:1 control-boundary contrast, `dir="auto"` on the mixed identifier, and safe-area padding are part of this interface contract. Center the wordmark independently of the back control, make it slightly larger only on desktop, and on mobile keep the logo header at the top while the remaining account group is centered in the available viewport. Identifier and password instructions live once in bold field labels; password values render LTR with right-side visibility toggles. The two password-step alternate actions split the row equally, use normal-weight underlined link styling, and have a visible pipe separator. The orange verification control remains the sole primary action. The store exit stays inside the card, full width but visually tertiary, and the first identifier step does not repeat that exit as an unlabeled header navigation choice.

### Integration authentication boundaries

`AuthenticationPolicy::session()` rechecks the current account, native-only role policy, identity binding, and blocks before Pinova creates a cookie. Its `pinova/authentication_policy` filter is deny-only: a callback cannot override a core rejection. Password authentication adds this final check inside the native `authenticate` pipeline and preserves upstream `WP_Error` instances. OTP policy is also checked before consumption and account creation. Public OTP registration never assigns the Dokan `seller` role.

`pinova/authentication_start` / `pinova/authentication_end` bracket Pinova cookie creation and native `wp_signon()`; `pinova/password_reset_start` / `pinova/password_reset_end` bracket Pinova password reset. The end actions run in `finally`. Adapters may scope only an identified incompatible callback and must restore its original priority and accepted arguments. An upstream `exit()` must be prevented before invocation; it does not execute `finally`. `OTPService::verify_with_flow()` returns an internal third `Identifier` value; do not expose it in public flow state.


### Mobile possession evidence

Read `pinova_mobile` with byte-exact distinct values: repeated identical physical rows resolve to one mobile without deletion or migration. Conflicting values still fail closed, as do duplicate proof, epoch and pending-flow records. WooCommerce customer display uses its view getter, never a synthetic unsaved data-store row; when extensions enable metadata caching, discard only zero/missing-ID mobile rows left in the old cache. Customer saves must preserve physical mobile rows and valid possession evidence.

`MobileVerificationService::is_verified($user_id)` requires a unique current mobile, current authentication eligibility, and HMAC evidence bound to the User ID, normalized number, revocation generation, timestamp, and signing salt. Historical flags, profile numbers, passwords, email OTPs, and mobile recovery are not possession evidence. Successful mobile login/registration OTPs mint it; `verify_mobile` OTPs instead update only the authenticated account and never create a session, account, or reset authority. The `pinova/mobile_verified($user_id)` action follows persisted evidence. Do not call `is_verified()` recursively from `pinova/authentication_policy`.

Authenticated `POST /pinova/mobile/request` and `/verify` require a REST nonce. Queue payloads remain encrypted and bind the account and OTP purpose; one account-bound queue reservation prevents unbounded number changes and lets privacy erasure cancel delivery to a not-yet-assigned number. Erasure and proof completion share a nonblocking database-namespaced account lock. Mobile metadata changes revoke evidence before and after mutation; identical value updates preserve it. Unsupported bulk deletion of mobile metadata is rejected because it cannot safely revoke per-account evidence.

The `[pinova_verify_mobile]` shortcode and dedicated query route render a separate form outside account forms. When an integration is saved enabled, ordinary account/profile edits cannot replace a login mobile without proof. An authorized administrator change invalidates evidence. Recovery state separately signs the verified identity type and keyed identity binding; reset start/end hooks receive `mobile`, `email`, or legacy `unknown` as their third argument. None of these origins imply mobile proof.


### wpForo membership and continuation

`Integrations\Continuation::validate()` consumes an already decoded return target, retains its query/fragment, and rejects another origin or an authentication loop. `MobileVerificationService::url($back_url)` encodes that validated nested target once; proof completion presents a validated continuation link.

The wpForo adapter intercepts native login/registration action dispatch before mutation and uses the one-argument URL filters. It marks only new Pinova accounts as owned pending members. Actual mobile proof can activate that pending transition only while registration is allowed and manual approval is off. Historical inactive accounts are not automatically enrolled or approved. Explicit administrator/moderator status changes control approval or a durable hold, including a same-value inactive write. The permission and topic/reply data filters add denials and remain effective for owned accounts when routing is off or dependencies are unavailable; they never grant a denied native permission.

Only the identified wpForo login/reset callbacks are scoped out, retaining their original priority and accepted argument count. Pinova mobile/unknown recovery cannot confirm email even with routing disabled. A genuine email reset may confirm its still-current address but never approves forum membership. Native non-Pinova entry points cannot lift owned pending restrictions. Guards use fresh status accessors because wpForo's generic member cache is not cleared by its profile reset API.

### Capability checks and REST rendering

IntegrationSettings checks the loaded public APIs and identified native callbacks separately for routing, membership, conversion, group preservation and reports. Versions are bounded diagnostic metadata, not runtime acceptance rules. wpForo does not depend on WooCommerce or Dokan. Missing membership or group-preservation capabilities leave the affected operation unavailable rather than approving pending members or converting sellers without protection; usable authentication routing stays independent. Requested Dokan coordination continues to guard native seller submission even when conversion is unavailable. Keep baseline/current, mixed and deployed combinations in the real-plugin CI matrix with HPOS on/off, and exercise native wpForo without commerce plugins.

The wpForo adapter completes native initialization at the end of successful REST authentication when wpForo has its base member service and callable initializer but no topic service. This compensates for upstream URI matching that misses query-based REST dispatch. Preserve the authentication result unchanged, do not initialize on WP_Error, do not initialize an already-ready service, and never redirect REST requests through forum login routing. This rendering fix remains independent of routing switches and dependency version strings. Exercise actual Elementor RecentTopics rendering through pretty and query-based REST URLs; a render-output filter runs too late to prevent the fatal.

IntegrationHealth exposes the same current capability snapshot in settings, Logs and Issues, incident JSON and read-only CLI. The current snapshot is independent of retained historical events. Safe administrator and daily-cleanup observations record bounded status changes without creating a scheduler, writing during report reads or bypassing the configured log level.
